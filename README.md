# CSC110 Explorations Path | Final Project

In the **Explorations** path, you’ll work in a **team of two or three** (or on your own, after consultation with your instructor) to build an interactive Python program on any topic you care about. Aim for a project roughly the size of **two to three CSC110 homework assignments** that draws on what you’ve learned in the course. You’ll design, build, test, and demonstrate your program together. Each person will also reflect on what they contributed and learned.

## What you’ll create

Choose a problem you want to solve or an experience you want to make. You might build a game, a tool for planning a major, an interactive poem generator, a fractal explorer, a graphing calculator, or a guide to campus resources. Start by identifying what you want someone to be able to do with your program.

| Area | What your project should demonstrate |
|---|---|
| **Core functionality** | The program fulfills its stated purpose. A user can complete its main tasks from start to finish. |
| **Meaningful interaction** | Users make choices or provide input that changes what the program does. Use terminal input or graphical controls and give users clear feedback. |
| **Clear, informative display** | Use graphics or formatted text to communicate what the user needs to know. For example, a game might show the current state of play, while a planning tool might display a labeled table of options. |
| **Data storage and reuse** | Store information in a form that lets the program retrieve, update, and reuse it efficiently at the scale of the project. A list or dictionary may be enough for data needed during a run. Choose storage that lasts across runs when users need to come back to the data later. |
| **Python programming and design** | Use conditionals, loops, and collections where they serve the task. Break the program into focused functions and group related functions into modules. |

Use GitHub to track your work. Your team can work on one computer and push from there, or work in parallel and coordinate changes through Git. Add a header to every Python file, write a docstring for every function, and comment decisions or logic that would be hard to understand from the code alone.

You may use additional imports, algorithms, or modules. Be prepared to explain the code you submit and how your program uses any imports. If you copy a code block, mark its boundaries with comments, cite the original source next to the block, and list it in the references at the top of the file. Teams using Pygame will be interviewed about their understanding of the project code.

Keep a brief, dated work diary as you go. Note what you did, how long you worked, whom you worked with, and what you plan to do next. You’ll use this record in your individual reflection.

## Design

Submit a design plan on Gradescope. Include your team members, project name, and a short description. Cover the following:

- **Program structure.** List the Python modules you expect to create and the main functions each will contain. Include a diagram showing how the pieces fit together.
- **User experience.** Walk through what a user will do and what the program will display in response. You can sketch screens, menus, or terminal output.
- **Data.** Identify information the program will need again later and describe how you plan to store and retrieve it.
- **Team workflow.** Explain how you’ll work together and use GitHub. Include when you plan to meet in and outside class.

## Prototypes and final submission

Fork this repository for your project code. Be sure to include the modules, data, images, and other files needed to run your code. Refer to supporting files using relative paths, such as `images/map.png`.

For each code milestone, commit and push the version you’re submitting to GitHub before submitting it on Gradescope. Keep `README.md` up to date with team information, a list of the project files and what they contain, any setup steps, and instructions for running and interacting with the program. One person submits the shared project files in Gradescope and adds their teammates to the group submission.

| Milestone | Program and code | User experience and documentation |
|---|---|---|
| **Prototype I** | Implement the smallest working version that demonstrates the project’s purpose. For example, an obstacle game might let the player jump on command while obstacles appear, with collision detection still to come. | Make the core interaction easy to try. Explain how to run it, what works, and which features are still in progress in the README. |
| **Prototype II** | Implement all planned features in a near-complete version. Test the main workflows and relevant edge cases. Keep a stable version available for Demo Day as you make changes. | Make the full workflow usable from start to finish. Refine controls, prompts, and output so someone else can try the program using the README. |
| **Demo Day** | Submit a stable demo version that shows the main features. Bring a machine on which the program runs. | Walk visitors through what the program does and let them see or try the main interactions. |
| **Final project** | Submit the complete program and all supporting files, incorporating bug fixes and other refinements since Demo Day. | Update the README to match the submitted version. Submit the group video and individual reflections described below. |
